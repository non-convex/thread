# 给模型用的 grep

这篇只讲一件事：Thread 的 `grep` 工具为什么不能把 ripgrep 的输出原样交给模型，以及我们改了哪几处。

如果你已经会用命令行搜代码，前面几节可以很快扫过。它们是给「听说过 grep、但没仔细想过它和 AI 的关系」的人准备的。

---

## 1. 人是怎么找一段代码的

写代码时你常常不是在「读整个项目」，而是在问一个很窄的问题。

比如：

- `TODO` 写在哪些地方？
- 这个函数名在哪里被调用？
- 哪几个文件提到了 `SessionTree`？

人的眼睛很擅长扫一份名单。你打开搜索结果，先看文件名，再决定要点开哪一个。噪声文件你会直接跳过。

命令行里做这件事的传统工具就叫 **grep**：给它一个词，它去文件里找包含这个词的行。

今天大家实际用的，多半是它的更快实现 **ripgrep**，命令名是 `rg`。Thread 底层也是调它。

你可以把它想成：一个只负责「在文本里找针」的引擎。它很快，也很老实。你问什么，它就按扫到的顺序把命中行吐出来。

---

## 2. 模型看到的不是屏幕，是配额

同样一份搜索结果，给人看和给模型看，负担完全不一样。

人看终端时：

- 可以滚动
- 可以略过
- 可以只点开两个文件
- 看完就可以忘掉剩下的

模型没有这些动作。工具一返回，整段文字就会进它的 **上下文窗口**。

上下文窗口是有上限的。进得去的每一个字，后面推理都要带着走。搜一个很常见的词，比如 `TODO`，项目里可能有几十上百处。如果把它们一次性平铺进去：

- token 被大量相似的行占满
- 真正相关的那两三处，可能排在很后面
- 后面一旦被截断，模型甚至看不见它们

所以问题不是「搜得准不准」。`rg` 通常搜得很准。

问题是：**搜索引擎的默认输出，是为终端设计的，不是为「只能读一次、而且有字数上限」的模型设计的。**

---

## 3. Thread 以前的 grep 做了什么

优化之前，Thread 的 `grep` 几乎是一层薄薄的套壳。

模型传来一个 `pattern`，可选再给一个 `path`。Thread 在工作区里跑：

```text
rg --line-number --no-heading --color never -- <pattern> <path>
```

然后把标准输出原样交给模型，最多截到 64KB。

这有几个具体后果。

第一，没有条数上限。高频词会一直灌，直到碰到那 64KB。Pi 至少还默认只留 100 条；Thread 当时连这个阀门都没有。

第二，结果是平铺的。每一行都是 `文件:行号: 内容`。同一个文件的 30 处 `TODO` 会变成 30 行彼此看起来差不多的文本。

第三，顺序是 ripgrep 扫盘的顺序。谁先被扫到，谁就排在前面。这和「哪个文件更可能是你正在改的」没有关系。

第四，截断切的是尾巴。前面塞满噪声之后，后面的重要文件会被直接砍掉。

对人来说，这只是一屏比较吵的搜索结果。对模型来说，这等于把垃圾先搬进了它的工作台。

---

## 4. 用一个小例子把问题看清楚

假设项目里只有三个文件：

- `src/app.ts`：1 处 `TODO`，而且你刚改过它
- `src/utils.ts`：1 处 `TODO`
- `src/noise.ts`：30 处 `TODO`，全是占位注释

你问模型：「项目里的 TODO 在哪？先看我正在改的。」

旧 grep 会返回大概这样的东西（缩写）：

```text
src/noise.ts:1: // TODO noise 1
src/noise.ts:2: // TODO noise 2
...
src/noise.ts:30: // TODO noise 30
src/app.ts:2: // TODO app
src/utils.ts:1: // TODO utils
```

如果第一页只能留下 20 行，模型看到的几乎全是 `noise.ts`。`app.ts` 要么挤在很后面，要么被截掉。

模型并没有「搜错」。它只是被一份**没有结构、没有主次**的名单淹没了。

后面几节的优化，都是在回答同一句话：

> 同样这些命中，怎样交给模型，才比较像一个编辑器的搜索面板，而不像把终端日志倒进聊天框？

---

## 5. 分组：先告诉它这是哪个文件

人看搜索结果时，第一个锚点通常是文件，不是行。

「`noise.ts` 里有 30 处」和「这里有 30 行长得很像的 TODO」，信息量差不多，但前者便宜得多。模型一旦知道「这是同一个文件里的重复噪声」，就可以决定要不要深挖，而不必把 30 行都当新信息读完。

所以现在的输出按文件成组：

```text
src/app.ts (1 match)
  2: // TODO app

src/utils.ts (1 match)
  1: // TODO utils

src/noise.ts (30 matches, showing 1–18)
  1: // TODO noise 1
  ...
  18: // TODO noise 18
```

同一文件的命中贴在一起。文件头上会写总数。如果这一页装不下整个文件，会写 `showing 1–18`，明确告诉模型：后面还有。

分组本身不丢信息，它只是换了一种更好读的摆法。

---

## 6. 排序：别让噪声文件靠数量抢首屏

分组之后，还有一个顺序问题。

如果仍然按扫盘顺序，`noise.ts` 还是可能排第一。30 条命中会把第一页占满。分组只是让这 30 条看起来整齐一点，首屏该被淹没还是会被淹没。

我们需要一个对「正在做的工作」更敏感的顺序。

Thread 没有去维护一套跨会话的「你常打开哪些文件」数据库。那会多一个索引、一种新状态，也和 Session Tree 现在管的东西不是一类。

它用了两个已经在工作区里的信号：

1. **Git 状态。** 你改过、暂存过、还没提交的文件，通常就是当前任务相关的文件。它们排最前。
2. **修改时间。** Git 看不出差别时，最近动过的文件靠前。

命中数量故意不参与争抢第一名。`noise.ts` 有 30 处 TODO，并不意味着它比刚改过的 `app.ts` 更值得先看。

所以上面那个例子，第一页会变成：

```text
32 matches in 3 files. Showing 1–20, ranked by git changes then recency.

src/app.ts (1 match)
  2: // TODO app

src/utils.ts (1 match)
  1: // TODO utils

src/noise.ts (30 matches, showing 1–18)
  ...
```

`app.ts` 只有 1 处，却因为有 git 改动排在最前。噪声还在，但它不再挡路。

---

## 7. 分页：一次只给一页，剩下的用 cursor 接着拿

即使排好了序，也不该一次倒完。

模型的下一步常常只需要前几处。它可能看完 `app.ts` 就去改代码，再也不需要那 30 处噪声。把它们提前塞进上下文，是纯浪费。

所以现在默认一页 **20** 条命中，上限 100。第一页末尾如果还有剩余，会带一句：

```text
[Continue with cursor="g1.…"]
```

模型若还想看，把这个 cursor **原样**传回来。Thread 知道这是同一次搜索的下一页，不会改词、改路径、改过滤条件。

cursor 是给机器续翻用的书签，不是给人读的。模型不需要理解它的编码，也不应该改它。

如果换了一个词还拿着旧 cursor，工具会拒绝。这是为了避免「我以为在搜 TODO，其实翻到了另一半 FIXME」。

和「截到 64KB 就停」不同，分页是有结构的停。模型知道自己只看了 1–20，也知道怎么要 21–40。旧逻辑砍尾巴时，它往往不知道自己错过了什么。

---

## 8. 有时候模型根本不需要行文本

还有一种更省的问法：「哪些文件提到了这个词？」

这时候行内容是累赘。只要路径和大致数量就够了。

所以有一个 `outputMode=files`：

```text
32 matches in 3 files. Showing files 1–3, ranked by git changes then recency.

src/app.ts (1)
src/utils.ts (1)
src/noise.ts (30)
```

排序规则和上面一样，只是不再附带每一行源码。模型可以先看地图，再决定对某一个文件做 `read`，或者把 `path` / `glob` 收窄后再 grep 一次。

这是同一件事的两种分辨率：`content` 看行，`files` 看文件。

---

## 9. 模型还可以先把搜索收窄

分页是结果侧的节流。更好的办法，是搜索时就别把网撒得那么大。

现在 `grep` 除了 `pattern`，还接受：

- `path`：只搜某个目录或某个文件
- `glob`：只搜某种文件，比如 `*.ts` 或 `src/**/*.ts`
- `literal`：把词当普通字符串，而不是正则
- `ignoreCase`：忽略大小写
- `context`：命中行上下多给几行，方便看周围代码

这些不是新发明，ripgrep 本身就会。以前 Thread 没把它们暴露给模型，模型只能搜完全部，再在一大坨结果里自己找。

一个比较健康的用法是：

1. 先 `outputMode=files`，看看命中落在哪些文件
2. 再对其中一个路径，用默认的 `content` 看行
3. 只有第一页不够时，才带 cursor 翻下一页

旧工具几乎逼着模型走相反的路：先把所有行吞下去，再在记忆里筛选。

---

## 10. 我们故意没做的事

有人用一套叫 FFF 的原生索引来换 Pi 的 grep。它更快，还会记住你常打开的文件，搜索结果带「使用习惯」。

Thread 没走那条路。

原因很具体。Thread 的核心承诺是：一个 checkpoint 绑的是工作区快照和对话上下文。它并不版本化「后台索引」或「跨会话的打开频率」。为了 grep 再养一个常驻索引，会多出一类工具自己的状态，和现有模型合不上。

所以排序信号只用工作区里已经有的东西：git 改没改过、文件最近动过没有。对「我正在改这个」通常够用。对「我三个月前常看那个文件」就不建模。

另外两件小事也值得知道：

- 默认**不搜隐藏文件**。Pi 的 grep 开了 `--hidden`，噪声面会更大。Thread 保持 ripgrep 的默认。
- `.gitignore` 仍然生效。被忽略的构建产物不会进结果。
- 机器上必须有 `rg`。Thread 不会替你下载它。

64KB 的硬截断还在，只是作为最后的安全网。正常一页 20 条，碰不到它。

---

## 11. 串起来看

还是那个三个文件的 TODO。

旧路径：扫到什么就输出什么 → 噪声排前面 → 截断砍尾巴 → 模型的上下文里全是 `noise.ts`。

新路径：

1. 仍然用 `rg` 把命中找全（内部最多扫 2000 条，防止极端仓库把工具拖死）
2. 按文件分组
3. 有 git 改动的 `app.ts` 提到最前
4. 只返回 20 条，并告诉模型怎么翻页
5. 模型如果只想看地图，可以改用 `files`

`rg` 还是那个 `rg`。变的是：**在它的输出和模型的上下文之间，加了一层为「有限注意力」准备的编辑。**

如果你记得一件事就够了——

> 对人，grep 是一份可以略过的名单；对模型，grep 必须是一页排好序的摘要。
