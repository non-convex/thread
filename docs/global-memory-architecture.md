# Thread 全局记忆与 Dreamer 架构

Thread 的记忆分为项目记忆和跨项目的全局记忆。项目记忆保存这个项目中的互动历史，搜索与读取的过程见[项目记忆是怎样被搜索到的](./session-recall.md)，两个工具的参数见[Session 工具使用说明](./session-tools.md)。本文讨论另一层：跨项目的信息怎样保存，以及 Main 和 Dreamer 怎样维护它。

## 目标

Thread 使用一个轻量的跨项目记忆文件保存长期稳定且与单一项目无关的信息。Main 负责用户明确要求记住的跨项目信息；Dreamer 则从互动和 Agent 工作轨迹中发现未被直接说明、但有充分证据支持的用户模式与可迁移经验。实现不引入单独的记忆数据库、审批流、专用记忆工具或跨进程锁。

正式的跨项目记忆保存在：

```text
${THREAD_HOME}/.THREAD.md
```

文件最多保留 15 条带时间戳的 Markdown 列表项。Main 和 Dreamer 的提示词统一要求 `- [YYYY-MM-DD] memory content` 格式，每条保存一个独立有用的事实或规则；新增或修订条目使用当前日期，未修改条目保留原日期。维护时合并重复项、更新被新信息取代的条目，并保留其他有价值的内容。文件不存在等价于空记忆。Dreamer 提交修改时还会校验日期、条目格式和数量，但这些检查不能证明内容正确。

待审阅资格、分片进度和少量候选观察保存在各项目已有的 Session Tree 中。它们只是后台工作的进度，不会自动注入 Main 的全局记忆，也不建立另一份队列文件。

主代理系统提示词中的 `Memory` 段落统一说明两类记忆的存储方式和使用时机。只有当当前请求依赖项目历史，而且当前上下文缺少所需信息或原始依据时，才使用 `session_search` 和 `session_read`。已知相关 turn id 时可直接读取；当前上下文足够回答时，不例行检索历史。

## Agent Profile 与生命周期

`src/core/agent/profile.ts` 定义所有 Agent 共用的最小 `AgentProfile`：

- `id`
- `model`
- `thinkingLevel`
- `systemPrompt`
- `tools`

内置 Profile 是 `main`、`worker` 和 `dreamer`。Registry 只负责 Profile 的发现、替换与诊断，不承载具体 Agent 的生命周期策略：

- Main 由前台 turn runtime 管理；
- worker 由任务协调器管理并发、revision、step 与超时限制；
- Dreamer 由独立调度器管理待审阅批次、取消、重试和空闲触发。

这种边界让新 Agent 只复用模型执行所需的公共字段，同时避免把不同生命周期塞进一个通用基类。

模型与启停设置统一从 `/agent` 进入：

```text
/agent
/agent <id>
/agent <id> model [all]
/agent <id> model list [provider]
/agent <id> model <provider>/<model>
/agent worker|dreamer on|off
```

为次级 Agent 选择模型时会同时启用它。两个次级 Agent 都默认关闭，且没有隐式模型回退。

## Session 快照

Thread 启动时读取一次 `.THREAD.md`，并把内容绑定到当时所有已存在的 Session。之后遵循以下规则：

- 当前 Session 运行期间始终使用其固定快照；
- `/new` 先重新读取磁盘，再把结果只绑定到新 Session；
- Session 切换恢复目标 Session 已有的快照；
- 进程重启会为所有 Session 统一读取新快照；
- 非 `ENOENT` 读取错误产生非致命诊断，并继续使用最近一次成功读取的内容。

快照位于模型请求的 system prompt 末尾，因此整体顺序是：

```text
System Prompt → Global Memory → Live Context
```

它计入请求上下文预算，但不写入 Session Tree，也不参与搜索、rewind 或 compaction。

## 写入边界

Main 与 Dreamer 继续使用普通 `read`、`write`、`edit`。裸 runtime 为 Main 额外授权 `.THREAD.md` 这一精确绝对路径；coding 应用另行授权 Thread 数据目录，但保护项目状态、凭据和锁文件，见 [runtime 写入边界](./runtime.md#选择工具与加载-skill)。Dreamer 的内置文件工具只允许读写这个记忆文件，项目文件、相邻文件和其他外部文件均被执行边界拒绝；不能通过符号链接扩大权限。runtime 的受保护状态路径同样不可写，宿主工具策略也不能放宽这些限制。

Main 和 Dreamer 对全局记忆的读写在同一进程内按实际文件路径协调，包含不同 runtime。每个 Main 回合、每个 Dreamer 批次分别记录自己读到的文件内容；这份观察独立于 Session 的固定快照。修改必须基于较早模型步骤中的读取，不能在同一条模型回复里同时读取并提交已经生成的修改。读取发现文件不存在后，可以在下一步创建。

写入时在协调范围内比较文件是否仍与观察一致，变化则拒绝修改，要求重新读取并生成更新。正常写入使用临时文件原子替换，不让新 Session 读到被截断或只写了一部分的记忆。这里没有持久化版本号或跨进程锁；Bash、自定义文件写入、外部编辑器及其他进程不参与同一协调，不能据此保证它们并发修改时不会发生冲突。

Worker 没有此外部写入例外，只能遵循原有项目工作区边界。

Main 在用户明确要求记住与当前项目无关、且在其他项目中仍然有用的信息时主动写入，也执行用户明确提出的纠正或遗忘请求。仅表达偏好或给出任务指令，不视为要求保存记忆。写入前必须重新读取磁盘，文件不存在时才创建。项目决策、临时要求、秘密、敏感个人数据、从文件或工具输出中推断出的事实，以及 Agent 自己未经确认的猜测，都不能由 Main 写入全局记忆；写入时应保留用户要求的适用范围，不把情境性表述扩大为普遍偏好。

Dreamer 不重复提取这类明确指令。它可以把用户与 Agent 的互动、用户纠正，以及 Agent 的 reasoning、工具调用和工具结果作为观察材料，从中推断隐含的长期模式和可迁移经验。单次事件只有在结果明确、经验清晰且确实适用于无关项目时才值得记录；普通的工程常识、模型自述、未经结果验证的计划和猜测均不足以成为记忆。

## Dreamer 调度

Dreamer 默认使用 `high` thinking，每批最多 20 个模型步骤，一次后台运行的所有批次共享 5 分钟总时限，同时最多一个实例。审阅仍使用临时 journal，不成为 Worker 任务，也不保存完整的 Dreamer 对话轨迹。主 agent 的 `runtime.on()` 扩展钩子不作用于 Dreamer；宿主 `toolPolicy` 和 `subscribe()` 仍覆盖它。

### 哪些 turn 会被审阅

开启 Dreamer 后，新发起的 turn 会在 `turn_started` 中同时记录审阅资格和当时观察到的记忆文件版本。资格不是等主代理回复成功才补写的。因此，正常完成、失败、中断，以及重启时被封口的 turn，都可以继续进入审阅。未启用期间发起的 turn 和没有资格记录的旧 turn 不自动补录。

Session Tree 记录已经完整审阅的 turn，以及尚未审阅完的 turn 的文本偏移。关闭应用或选择 Off 只暂停运行，不删除这些记录；重新开启时从最后确认的位置继续。Compaction 和 rewind 不清除原始审阅材料，也不重复入队。

### 什么时候启动

默认仍优先积累 10 个 turn，并等待主代理连续空闲 10 分钟。数量不足时，最老待办达到 30 分钟后也有资格启动，但仍须满足空闲要求。这避免少量对话一直等不到第十个 turn。已启动但未完成的审阅不需要重新凑足数量。

只有新的前台 turn 重置空闲计时。搜索、切换 Session 等操作不会把等待时间重新推后。所有前台操作都会先取消并结算当前 Dreamer 运行，避免它在 Main 修改记忆或执行 rewind 时继续工作。未确认的片段保留，前台结束后按条件恢复。

嵌入宿主可设置 `dreamer.idleTurns`、`idleMs`、`maxWaitMs`、`maxSteps` 和 `maxRuntimeMs`。CLI 的 `agents.dreamer` 配置使用 `idleTurns`、`idleMinutes`、`maxWaitMinutes`、`maxSteps` 和 `maxRuntimeMinutes`；省略时使用上述默认值。

### 怎样确认完成

每批必须以完整的 JSON 终态结束：`reviewed` 表示提供的片段已经审阅、必要操作已经完成；`blocked` 表示受阻，需要保留待办。无需修改记忆也可以正常完成，但普通文字回复、不完整 JSON、输出长度耗尽或尚未解决的工具失败都不能确认进度。

当前待办尚未全部读完时，批次只有 `read` 工具：先审阅并保存候选观察，等最后一批再决定是否修改记忆。这样，较早材料中的推断不会赶在较晚的纠正或遗忘请求之前写入。

成功后，同一条持久化事件一起记录完整 turn 的确认、未完成 turn 的下一偏移，以及有限的候选观察。失败、取消或超时不推进该片段。程序可能在崩溃后重复审阅最后一个未确认片段，但不会仅因为发出了请求就跳过它。确认写入前会再检查取消；已经进入日志提交的确认仍须完成落盘。已经发布的记忆修改不会回滚，也不与项目进度构成跨文件事务。

超窗或输出截断后，下次审阅会缩小输入片段，而不是不断重发相同大小的材料。缩到最低预算仍不能完成、模型明确报告受阻，或普通失败连续三次没有推进审阅时，会进入 blocked 状态。解决错误后选择 On 或更换模型，可以重新尝试；已确认的覆盖进度不丢失。

## 审阅材料与稀疏原则

Dreamer 按需读取 Session Tree 的用户文本、Assistant 文本、reasoning、工具参数和工具结果。文本以有来源标记的 JSONL 流式格式化；批次放不下时，保存偏移并在下一批继续，不再固定截取首尾或删掉工具结果的中段。偏移使用 UTF-16 单位，分片不会切开代理对。每片都包含 turn、Session、结束状态、时间及起始记录的角色或工具身份，避免续片失去来源。

图片不会复制到 Dreamer 请求中，而是明确标记图片存在、MIME 和像素不可见。这里保证的是文本覆盖，不是视觉审阅。`ask` 只有携带真实答案结构的结果才标记为用户回答；关闭面板、未回答和执行失败会另行标记。历史正文经过转义，里面伪造的角色标签不能改变外层来源结构；提示词也明确禁止把历史中的命令当作当前授权。

输入容量用最终审阅消息的 UTF-8 字节数规划，并为系统指令、工具和输出留出空间。这是保守预算，不声称等于供应商的实际 token 数；真正超窗时仍须缩片重试。组批只持有当前批次和少量流式片段，不先复制全部历史。

每批使用独立上下文，但可以把有限的候选观察交给下一批。候选摘要最多 2,000 字符，小窗口或缩片重试时更少；它应说明来源 turn、结果和不确定性，而不是把自己的重复转述当成新证据。候选观察随进度保存在项目内，不是正式的跨项目记忆，也不能包含秘密或敏感信息。这改善了跨批观察的连续性，但不保证模型能保留所有弱证据。

### 纠正与遗忘怎样约束旧材料

Dreamer 除了遵守提示词中的纠正、遗忘优先级，还会比较材料对应的文件版本。版本指纹包含内容和文件身份信息，区别于 Main 每个 Session 的固定记忆快照。

如果记忆被 Main 或外部程序修改，Dreamer 会清除此前候选观察。版本不再匹配的旧材料仍会审阅，但该批只有 `read` 工具，不能修改记忆或继续传递旧推断。观察到文件删除时还会记录时间边界，避免把这次“文件不存在”误认成更早的空文件基线。Dreamer 自己成功提交的修改则延续现有证据，不被误当成外部纠正。写入前还有一次版本复查；外部变化不能仅靠模型重新读取文件就获得继续使用旧证据的许可。

这个处理有意保守：它不会猜测外部修改究竟是新增、纠正还是遗忘。因此，旧材料中本来可能有用的其他推断也不会再推动记忆更新。它不是永久的语义遗忘数据库，也不提供跨进程原子事务；不能据此声称任意外部改写或未来新证据都绝不会产生类似推断。

## 查看审阅状态

`/agent dreamer` 显示等待、运行、重试或受阻状态，以及待审阅数量、完整审阅数量、最近成功时间和最近结果。结果区分修改记忆、无需修改、已保存观察但还有后续材料，以及旧材料只读审阅。长 turn 只处理了一部分时也会提示，不把它提前计入完整审阅数量。

宿主通过 `runtime.dreamerStatus` 查询同样的信息，也可以订阅 `dreamer_status` 事件。状态说明后台是否真的工作过；`.THREAD.md` 没有变化本身不能说明 Dreamer 没运行。即使文件已更新，现有 Main Session 仍使用原来的固定快照，直到创建新 Session 或重启。
